# Эксплуатация и восстановление

## Назначение Compose

`compose.yaml` обеспечивает воспроизводимый локальный стенд и CI.
Для приложения используется один runtime-образ, non-root пользователь,
read-only файловая система, `tmpfs`, сброшенные capabilities и ограниченные логи.
Секреты передаются через окружение, `.env` не включается в образ.

Локальная инфраструктура содержит один PostgreSQL, один Redis, один Kafka broker
и одно S3-хранилище. Высокая доступность и резервное копирование на этом стенде
не заявляются. Для production используются отдельные инфраструктурные сервисы
и необходимые гарантии хранения.

## Конфигурация production

При `APP_ENV=production` предусмотрена проверка обязательных настроек:

- Случайный `APP_SECRET_KEY` не короче 32 символов и отдельный `METRICS_TOKEN`.
- Явный список `ALLOWED_HOSTS`, ограниченный список CORS origins.
- PostgreSQL с проверкой TLS-сертификата: `DATABASE_URL` с `?ssl=verify-full`.
- Redis через `rediss://`.
- Kafka через `SSL` либо `SASL_SSL`; при SASL задаются username/password.
- Репликация новых топиков Kafka не ниже `3`, минимум подтверждающих реплик `2`.
- HTTPS для явно настроенного S3 endpoint либо стандартный HTTPS endpoint AWS.
- Удалённые `SEED_ADMIN_PASSWORD` и `SEED_EMPLOYEE_PASSWORD`.

Пример генерации секретов:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Команда выполняется отдельно для каждого секрета. Конкретные значения хранятся
в выбранном secret manager или приватных файлах окружения. Для собственных CA
сертификаты монтируются в контейнер; для Kafka используется `KAFKA_SSL_CAFILE`,
для PostgreSQL — настройки SSL, поддерживаемые asyncpg / `PGSSLROOTCERT`.

`APP_ENV=production` отключает публичные Swagger/OpenAPI и demo seed.
Это не переключает локальные брокеры и БД на TLS автоматически.
Нужные инфраструктурные сервисы и сертификаты подготавливаются до запуска приложения.

## Права и запуск

Для миграций применяется отдельная роль владельца схемы. Runtime-пользователю
БД выдаются права на нужные таблицы и последовательности; права `CREATE`,
изменения триггеров и управления ролями не требуются.
Файл с учётными данными миграций не передаётся API и воркерам.

Порядок развёртывания:

1. Подготавливаются PostgreSQL, Redis, Kafka topics и приватный S3 bucket.
2. Проверяются секреты, TLS, правила доступа и резервное копирование.
3. Собирается неизменяемый образ `docker build --target runtime -t shiftledger:<version> .`.
4. Отдельной задачей с миграционной ролью выполняется `alembic upgrade head`.
5. Запускаются API, Outbox publisher и Reconciliation worker.
6. Проверяются readiness, consumer lag, Outbox backlog, ошибки и метрики.

Инструмент `python -m shiftledger.cli bootstrap` идемпотентно создаёт отсутствующие
топики и бакет. Для него используются отдельные инфраструктурные права.
Для уже существующих топиков настройки не переписываются: partitions,
replication factor, min ISR и retention проверяются средствами управления Kafka.

Для первой организации предусмотрен provisioning без публичной регистрации:

```bash
python -m shiftledger.cli create-organization --name "Store" --admin-email owner@example.com
```

Пароль вводится скрыто. В автоматизированной задаче доступен `--password-env`
с именем переменной окружения; пароль не передаётся аргументом командной строки.
Проверка существующего аккаунта не меняет его пароль. Приглашения и подключение
существующих пользователей к новым организациям находятся в roadmap.

Права S3 ограничиваются конкретным бакетом/префиксом. Скачивание проходит через
авторизованный API; бакет не делается публичным. Производственные изображения
и распознанные данные требуют политики доступа, хранения и удаления.

## Reverse proxy

API запускается с `--no-proxy-headers` по умолчанию. При размещении за доверенным
proxy включаются `--proxy-headers --forwarded-allow-ips=<адреса доверенных proxy>`.
Доступ клиентов напрямую к порту API ограничивается сетью.
Доверять произвольному `X-Forwarded-For` нельзя: от IP зависит ограничение входа.

На proxy задаются HTTPS, лимит тела запроса, таймауты и правила доступа к `/metrics`.
Максимальный размер фото по умолчанию 8 МиБ, JSON-запроса 512 КиБ;
для multipart предусмотрен дополнительный запас 1 МиБ.

## Состояние процессов и метрики

- `/health/live` проверяет, что API отвечает.
- `/health/ready` проверяет PostgreSQL, Redis и S3.
- API сохраняет отчёты через Outbox и не требует доступности Kafka при отправке.
- Worker healthcheck проверяет свежесть heartbeat; это проверка активности процесса.
- Неисправность Kafka отслеживается также по consumer lag, backlog и ошибкам публикации.

Docker сам по себе не перезапускает контейнер только из-за `unhealthy`.
Restart policy применяется при завершении процесса; в production используются
соответствующие проверки оркестратора и алерты.

API-метрики находятся на `/metrics`; при настроенном `METRICS_TOKEN` требуется
`Authorization: Bearer <metrics-token>`. Воркеры экспортируют метрики на внутренних
портах `9101` и `9102`, которые не публикуются Compose на хост.

Основные метрики:

- `shiftledger_http_requests_total`, `shiftledger_http_request_duration_seconds`.
- `shiftledger_outbox_published_total`, `shiftledger_outbox_failures_total`.
- `shiftledger_processed_events_total{outcome="processed|duplicate|dead_letter"}`.

Для Outbox добавляется операционный запрос:

```sql
SELECT count(*) AS pending,
       min(created_at) AS oldest_pending,
       max(attempts) AS max_attempts
FROM outbox_messages
WHERE published_at IS NULL;
```

По мере нагрузки требуются алерты на возраст Outbox, lag группы,
рост DLQ, ошибки/latency API, нехватку диска и состояние резервных копий.
Метрики используют шаблон маршрута; пользовательские ID не становятся labels.
Тела отчётов, пароли, токены и содержимое чеков не включаются в логи приложения.

## Kafka и DLQ

Топики:

| Топик | Назначение | Локальное хранение |
| --- | --- | --- |
| `shiftledger.report-submitted.v1` | Отправленные отчёты | 7 дней |
| `shiftledger.reconciliation-completed.v1` | Завершённые проверки | 7 дней |
| `shiftledger.reconciliation-dlq.v1` | Необработанные сообщения | 30 дней |

Производственный retention выбирается по максимальному допустимому простою,
восстановлению и объёму событий. Длительность хранения Inbox должна покрывать
возможные повторные доставки. Автоматическая очистка Inbox/Outbox в каркасе
не включена; данные не удаляются без согласованного срока.

Просмотр локальной DLQ:

```bash
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka:9092 --topic shiftledger.reconciliation-dlq.v1 \
  --from-beginning --max-messages 10 --timeout-ms 10000
```

После устранения причины валидное событие повторно отправляется:

```bash
docker compose exec reconciliation python -m shiftledger.cli replay-dlq --partition 0 --offset 0
```

Указываются реальные partition/offset записи DLQ. Сохраняется исходный event ID,
поэтому уже обработанное событие остаётся безопасным повтором. Повторная доставка
не удаляет запись DLQ. Некорректная схема сначала исправляется контролируемой
операцией; replay-команда не преобразует неизвестную схему автоматически.
Сообщения больше 64 КиБ сохраняются в DLQ с усечённым payload и полным SHA-256;
автоматический replay усечённых сообщений отклоняется.

## Проверка восстановления

На локальном стенде можно временно остановить только сервис этого проекта:

```bash
docker compose stop kafka
```

Новый корректный отчёт должен сохраниться и возвращать `pending`, а его событие
должно остаться в Outbox. После восстановления брокера:

```bash
docker compose start kafka
```

Publisher повторяет доставку; consumer сохраняет результат. Доступность Redis
и S3 проверяется отдельно. API отклоняет вход при недоступности Redis;
получение уже опубликованного шаблона использует PostgreSQL как fallback.

## Резервные копии и обновления

Для production необходимы резервные копии PostgreSQL с проверкой восстановления,
PITR по выбранным RPO/RTO, защита S3-объектов и политика Kafka retention.
Восстановление проверяется в отдельном окружении с согласованными consumer offsets
и состоянием Inbox; очередь не заменяет резервную копию БД.

Обновление Python-пакетов выполняется через `uv lock --upgrade` с повторными
проверками. Для отдельного пакета применяется `uv lock --upgrade-package package-name`,
после обновления окружение синхронизируется командой `uv sync --locked`.
`pyproject.toml` и `uv.lock` сохраняются вместе при изменении зависимостей.
Образы обновляются вместе с tag/digest и проверкой миграций.
CI проверяет известные уязвимости runtime-зависимостей через `pip-audit`.
Сканирование контейнеров и нагрузочные сценарии добавляются к процессу выпуска
под выбранный registry и окружение.

Объекты S3 без метаданных и неиспользованные загрузки требуют отдельной
процедуры очистки с задержкой и проверкой ссылок. Чистка работающей инфраструктуры
не выполняется автоматически при старте приложения.
