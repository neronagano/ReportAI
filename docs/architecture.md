# Архитектура и принятые решения

## Границы каркаса

Добавлен модульный монолит с общей PostgreSQL и независимыми процессами API,
Outbox publisher и Reconciliation worker. Эти процессы собираются из одного
пакета и образа, а масштабируются отдельно.

Реализован один законченный сценарий: публикация шаблона, загрузка изображения,
отправка отчёта, событие Kafka, проверка и получение результата через API.
Пользовательский интерфейс, OCR и ИИ-агент находятся в roadmap.

## Структура модулей

```text
src/shiftledger/
├── api/               # HTTP-зависимости, request ID, ограничения тела запроса
├── identity/          # Пользователи, организации, роли и аутентификация
├── templates/         # Определения форм, версии, валидация значений
├── reports/           # Отправка неизменяемого отчёта и идемпотентность
├── attachments/       # Права на файлы, проверка изображений, S3-адаптер
├── reconciliation/    # Арифметика сверки, историческая база, результаты
├── intelligence/      # Контракты распознавания и объяснения результатов
├── messaging/         # Конверт события, Kafka, Outbox и Inbox
├── workers/           # Процессы, обработка ошибок, остановка, heartbeat
├── resources.py       # Создание и закрытие инфраструктурных ресурсов
├── database.py        # DeclarativeBase и фабрика сессий
├── config.py          # Типизированная конфигурация окружения
├── observability.py   # Логи и метрики
└── cli.py             # Bootstrap, demo seed, provisioning, DLQ replay
```

Внутри функциональных модулей используются `domain.py`, `models.py`, `schemas.py`,
`service.py`, `router.py` по необходимости. Доменные правила не импортируют
FastAPI, Redis, Kafka или ORM. Сервисный слой управляет прикладной операцией,
HTTP-слой проверяет права и преобразует ответ, инфраструктурный слой выполняет I/O.

Для работы с ORM применяется SQLAlchemy напрямую. Отдельные repository-классы
не добавляются к каждому CRUD-методу; протоколы предусмотрены на границах,
где замена реализации имеет смысл: object storage, публикация событий и ИИ.
Полная независимость сервисов от SQLAlchemy не заявляется.

## Транзакции

Добавлена функция `get_session` с зависимостью `scope="function"`.
Для каждого запроса открывается одна транзакция; все зависимости используют
одну сессию. Commit выполняется до отправки успешного HTTP-ответа.
Воркеры открывают собственную транзакцию на событие или запись Outbox.
Одна `AsyncSession` не разделяется между параллельными задачами.

При конкурентной отправке отчёта используются уникальные ограничения
PostgreSQL и savepoint. Пара `(organization_id, submitted_by, idempotency_key)`
идентифицирует запрос; SHA-256 канонического тела запрещает использовать
один ключ для разных данных. Повтор возвращает исходный отчёт с `200`;
новая отправка — `201`; конфликт — `409`.

В каркасе предусмотрен один отчёт на организацию, точку, бизнес-дату и смену.
Разделение отдельных отчётов нескольких сотрудников одной смены требует
явной модели назначений и отдельного правила уникальности.

## Версии и смысл полей

Опубликованная версия хранит полный JSON-снимок определения. Отчёт ссылается
на её UUID. Изменение шаблона создаёт следующую версию с блокировкой родительской
записи. Номера версий защищены уникальным ограничением.

Пара `block.key / field.key` обозначает стабильную идентичность поля.
Название можно уточнить, тип, финансовую семантику и кратность существующего
ключа изменить нельзя. Проверяются все предыдущие версии, включая удалённые
и затем возвращённые поля. Смена валюты требует нового шаблона.

Стартовая миграция добавляет PostgreSQL-триггеры, запрещающие `UPDATE` и `DELETE`
опубликованных версий и отправленных отчётов. Дальнейшие исправления должны
проектироваться отдельными ревизиями с автором, причиной и ссылкой на оригинал.
Прямой SQL владельца БД остаётся административной границей доверия.

## Денежные данные и сверка

В динамических JSONB-полях деньги нормализуются в строки с двумя знаками:
`"1250.50"`. JSON float, `NaN`, экспоненциальная запись и более двух знаков
отклоняются. Расчёт выполняется через `Decimal`, итоги сохраняются в `NUMERIC(20,2)`.
Финансовые семантики назначаются обязательным неотрицательным полям.

```text
Ожидаемая касса = открытие + продажи наличными − возвраты − расходы из кассы − инкассация
Отклонение = фактическая касса − ожидаемая касса
```

Для полной сверки требуются все шесть семантик. Пустой повторяемый блок
расходов означает явно заявленный нулевой расход. При отсутствии необходимых
полей возвращается `cash_check_incomplete`, денежные итоги остаются `null`.

Историческая база выбирается за предыдущую **бизнес-дату**, для той же
организации, точки, смены и шаблона. При отсутствии базы возвращается
`baseline_missing`. Изменение выручки выше порога отмечается как отклонение;
оно само по себе не доказывает недостачу. Нулевой знаменатель обрабатывается отдельно.

Результат сохраняет UUID базового отчёта и показатели, на которых построены выводы.
В текущей версии это снимок на момент обработки. Поздний отчёт за предыдущий день
не запускает автоматический пересчёт уже сохранённых результатов.

## Доставка событий

1. API сохраняет отчёт, ссылки на вложения и запись Outbox в одной транзакции.
2. Publisher выбирает одну готовую запись через `FOR UPDATE SKIP LOCKED`.
3. Событие отправляется с `acks=all` и идемпотентным Kafka producer.
4. После подтверждения брокера сохраняется `published_at`.
5. Consumer вставляет Inbox, результат и событие завершения в одной транзакции.
6. Kafka offset подтверждается только после успешного commit PostgreSQL.

При сбое между подтверждением брокера и commit Outbox возможна повторная
доставка. Уникальный Inbox `(consumer_name, event_id)` и единственный результат
на отчёт делают повтор безопасным. Блокировка отчёта защищает также от двух
разных ID событий, указывающих на один отчёт.

Гарантия между PostgreSQL и Kafka — **at least once**. Kafka producer idempotence
не превращает два независимых хранилища в общую транзакцию.
На время отправки удерживается одна блокировка Outbox с таймаутом 15 секунд.
Это осознанное упрощение каркаса; при измеренной высокой нагрузке можно перейти
на lease/claim-механизм или CDC без изменения контракта события.

При ошибке публикации запись остаётся в Outbox с backoff до 300 секунд;
лимита, после которого она удаляется, нет. Consumer выполняет до пяти попыток
с backoff. Необрабатываемое сообщение переносится в DLQ, после подтверждения
DLQ подтверждается исходный offset. Если запись в DLQ не удалась, offset не
подтверждается и сообщение остаётся доступным для повторной доставки.

Ключ партиционирования — UUID отчёта. Kafka гарантирует порядок внутри
партиции; глобальный порядок разных отчётов не предполагается.
В конвертах передаются UUID, версия, тип и correlation ID; текст сотрудников
и байты изображений в топики не включаются.

## Redis

В кэше используется ключ с организацией и UUID неизменяемой версии.
Проверка членства выполняется до доступа к кэшу. Ошибка кэширования не мешает
получению шаблона из PostgreSQL. БД остаётся источником истины.

Ограничение входа выполняется атомарным Lua-скриптом по хешу IP.
Если Redis недоступен, вход временно возвращает `503`. В production реальный
IP должен передаваться только доверенным reverse proxy. По мере развития
потребуются отдельные лимиты на аккаунт и регистрационные/восстановительные операции.

## Вложения

Изображения сохраняются в приватном S3-бакете по серверному ключу
`organization_uuid/attachment_uuid.extension`. Пользовательское имя файла
не используется как путь. Проверяются фактический формат и структура изображения,
размер тела запроса, размер файла, число пикселей, организация и владелец.
В PostgreSQL сохраняются тип, размер, SHA-256, автор и связь с отчётом.

S3 не участвует в SQL-транзакции. Ошибка первичного сохранения метаданных
вызывает компенсационное удаление объекта. При позднем сбое commit всё равно
возможен объект без записи; при эксплуатации нужен периодический поиск таких
объектов с безопасным сроком ожидания. Автоматический GC находится вне текущего каркаса.

Приложение принимает только изображения. PDF, антивирусная проверка,
карантин файлов и прямые presigned-загрузки требуют отдельного этапа реализации.

## Граница ИИ

Добавлены типизированные `ReceiptExtraction`, `ReviewContext`, `BusinessReview`
и протоколы провайдеров. Извлечение содержит сумму, дату, позиции, источник,
уверенность и неопределённости. ИИ-находки содержат ссылки на вложения и поля,
а также обязательную необходимость проверки человеком.

При подключении провайдера исходные значения сотрудников, извлечённые данные
и результаты анализа должны храниться отдельно. Финансовая арифметика остаётся
в доменных правилах. Распознанная сумма не должна автоматически перезаписывать отчёт.
Для агента предусматриваются разрешённые инструменты чтения с проверкой
организации; инструкции внутри чеков и комментариев считаются входными данными.

Добавление LangGraph, модели, OCR-движка, версий prompt и набора evals выполняется
после выбора первого бизнес-сценария и набора реальных документов.
